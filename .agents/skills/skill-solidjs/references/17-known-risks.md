# Known risks of the verified base

Base: [verified revision](../SKILL.md), `solid-js` and `@solidjs/web` at commit `ee49b3e`, reverified on 2026-09-29. Each entry says whether the fix is in the verified base: the tag of that base contains the commit of the fix (comparison `<fix>...ee49b3e` with status `ahead`) and, when possible, a local probe with a control on the previous base (`9a29b1a`) or a line of the `dist` confirms it. They are not a current query of the registry. A closed issue, a merged PR or a version in the `package.json` of a branch do not prove a fix in the installed package. This is the only reference with upstream status; the others point to the R entry. It is neither an exhaustive list nor an upgrade recommendation. The upstream sources are next to each risk; the upstream tests were not run locally.

## R01: subscription retention during a pending action

Sources: [issue #3543](https://github.com/solidjs/solid/issues/3543), [fix #3547](https://github.com/solidjs/solid/pull/3547), [test of the fix](https://github.com/solidjs/solid/blob/0ba30d374befd6b31cf7c27496b817fb3b3072d2/packages/web/test/zombie-show-leak-3543.spec.tsx).

Contract: with `Show` and a nested memo generated by the compiler, an unrelated action still open retained subscriptions on the previous base. Fixed on the verified base: the recomputation keeps `REACTIVE_ZOMBIE` (`@solidjs/signals/dist/dev-shared.js`); without a local probe, because the scenario requires compiled DOM. The fix does not prove that all extra work under a transaction was removed.

Approach: when investigating CPU or retention, compare a control without an open action with the same scenario under a pending action; measure before, during, after the settle and after dispose. Do not introduce a global remount nor a patch in node_modules as a first answer.

## R02: item visually duplicated between filtered lists

Sources: [issue #3548](https://github.com/solidjs/solid/issues/3548), [fix #3558](https://github.com/solidjs/solid/pull/3558).

Contract: a stream, an optimistic store, keyed lists and overlapping confirmations could duplicate an item in the DOM from a single collection on the previous base. Fixed on the verified base (a lane pass over a superseded overlay reads the displayed override, `@solidjs/signals/dist/dev.js`); without a local probe. It is a fix distinct from R01.

Approach: record IDs per column in the model and in the DOM, keep the order of submission and confirmation and reduce the reproduction. Do not make up a random key to hide the duplication nor drop authoritative records. Serializing mutations per entity is a mitigation to test, not a proven fix.

## R03: on and a boundary created during a hold

Sources: [issue #3540](https://github.com/solidjs/solid/issues/3540), [change of Loading.on](https://github.com/solidjs/solid/pull/3556), [change of on and latest](https://github.com/solidjs/solid/pull/3575).

Changed on the verified base. On the previous base, `on` compared values, a sibling reader of the same source held the update and `on={latest(x)}` with a sibling reader was also held.

Contract on the verified base (graph without DOM, with a control on the previous base): `on` is a list of dependencies. The runtime evaluates `props.on` tracked and every rerun rearms the boundary without comparing values, so `on={id() > 0}` shows the fallback when `id` changes. `on={id}` does not call the accessor and stays equivalent to leaving `on` out. The fallback arrives with the frame that caused the change: with a sibling reader of the same source, `on={id()}` stays without a fallback and fires `LOADING_ON_OUTSIDE_HOLD` in dev. `on={latest(id)}` shows the fallback right away, next to the content that the sibling holds. An `on` that reads the async data shows the fallback on each `refresh`; `on={id()}` with a `refresh` of the same subject keeps the content. `Errored` does not accept `on` (the runtime only reads `children` and `fallback`).

Approach: write for the installed package. Use `on={latest(id)}` when the fallback must show right away, and handle `LOADING_ON_OUTSIDE_HOLD` by reading `latest()` in `on` or by moving the outer read inside the boundary. Do not use mutable counters or always new objects in the read of `on`. When switching RCs, repeat the [boundaries](08-async-loading-errors-and-recovery.md) matrix before changing the guidance.

## R05: server function calls across origins

Sources: [issue #3538](https://github.com/solidjs/solid/issues/3538), [fix #3549](https://github.com/solidjs/solid/pull/3549).

Contract: on the previous base, the runtime refused a request marked same-site/cross-site before consulting the origin matcher, without a CORS policy for that flow. The `@solidjs/web` of the verified base carries the fix: with an `Origin` present and listed in `csrf.origin`, the call passes and gets `Access-Control-Allow-Origin` and a preflight response; an `Origin` outside the list, a missing one or `Sec-Fetch-Site: none` stay at 403, and without a configured `csrf.origin` no other origin is admitted. The exception is the functions declared with `GET()`: their GET and HEAD skip the origin gate by default (`csrf.protectDeclaredReads` is false) and accept a call from another origin with the cookies of the environment; method rules in [13](13-server-functions-and-security.md).

Approach: list in `csrf.origin` only trusted page origins and do not turn off CSRF to solve a 403. Declare with `GET()` only reads without side effects and use `csrf.protectDeclaredReads: true` when the deploy does not depend on a cache shared by origin. Credentials require `allowCredentials: true`; keep `SameSite=None; Secure` for the cookie that must cross sites and prefer a bearer token through `prepareRequest`. Validate transport, preflight, origin and credentials in a real browser; a `curl` that calls the endpoint does not prove that the browser can read it.

## R07: `textContent` loses the numeric zero in the SSR HTML

Sources: [SSR compiler in the verified revision](https://github.com/solidjs/solid/blob/ee49b3eee5f457a637075c4a3bbdcee013808fc3/packages/compiler/src/ssr/transform.rs#L2386), [textContent contract](https://v2.solidjs.com/reference/solid-web/jsx-properties/text-content).

Contract (still present on the verified base: native compiler and `renderToString` reverified): for `<p textContent={p.value}/>` in hydratable SSR, the compiler emits `escape(p.value || " ")`, and the placeholder uses truthiness. `renderToString` produces `<p _hk=0> </p>` for `0` and for `""` and `<p _hk=0>1</p>` for `1`; the type accepts `string | number` without a caveat. On hydration (happy-dom with a minimal bootstrap and a full build in Chromium, dev and production), the client keeps the space until the first update and then recovers `"0"` in the same Text node; updates to literal markup, empty and zero work. Explicit children suppress `textContent` at compile time.

Limit: the negative control confirmed a structural mismatch warning in dev, without proving that the runtime diagnoses a textual divergence.

Approach: do not recommend `textContent` as a general optimization nor for numbers that can be zero in SSR pages; prefer plain JSX. `String(value)` is a workaround hypothesis without validation with empty, hydration and the domain.

## R08: a late async rejection during SSR takes down the Node process

Sources: [issue #3570](https://github.com/solidjs/solid/issues/3570), [issue #3569](https://github.com/solidjs/solid/issues/3569).

Contract on the previous base: with `renderToString`, an async memo that rejects after the render returned the fallback becomes an unhandled rejection and the process exits with code 1, even under an `<Errored>` around `<Loading>`. The same holds for `createStore`, `createProjection` and `createOptimisticStore` in the derived form and for an async generator that throws before the first `yield`; a generator that fails after the first value is not affected. With `await renderToStream()` and a rejecting read as a direct child of `<Loading>`, without an `<Errored>` above and with `onError` provided, the call throws a `TypeError` in `traceMetaMarkup`, the Promise never settles and the process also exits with 1. In a compiled HTTP host, the response goes out with 200 and without a leak, and the process dies milliseconds later. Fixed on the verified base: the same probe serves the fallback and the process stays alive, with and without `<Errored>`; `await renderToStream()` with a direct child read resolves and calls `onError` once.

Limits: `renderToStream().pipe()` and `await renderToStream()` under `<Errored>` did not reproduce (an observation, not a certified mitigation); `pipeTo` was not exercised. The sanitization of render failures under a boundary does not cover that path.

Approach: on the server, turn expected failures into a result or a public error before returning them to the graph; an `Errored` on the client does not protect the process. Treat a process exit as a symptom of this risk before suspecting the adapter. Reproduce the scenario in a disposable server: on the previous base, it takes down the following tests with `ECONNRESET`.

## R09: a read right after a write in a derived store changes after a `latest`

Sources: [issue #3576](https://github.com/solidjs/solid/issues/3576).

Contract: in a derived store (`createStore(() => ({ value: 0 }), { value: 0 })`), five writes in a row through the setter, each followed by a read outside the setter and without `flush`, return `0,1,2,3,4`. On the previous base, after a single `latest(() => store.value)` call before the sequence, they returned `0,1,0,0,0`; on the verified base they return `0,1,2,3,4` in that case too. With `flush` after each write, `0,1,2,3,4`. In a plain store (`createStore({ value: 0 })`) the reads return `0,0,0,0,0` with or without `latest`: outside the setter, the read sees the previous value until the batch settles. The value after `flush` is `4` and a render effect only sees `0` and `4`. Cause on the previous base: the `latest()` shadow installed an override without an owning transaction; the fix is in the verified base. Limit: graph without DOM; not tested with compiled JSX, an open action or SSR.

Approach: do not decide logic by reading the store right after the setter, in any form; keep the value in a local variable or read inside the draft. In tests, call `flush` before asserting. Do not use `latest` outside JSX or a memo to "read the new value".

## R10: a late write through the draft of a projection is dropped without a warning

Sources: [issue #3585](https://github.com/solidjs/solid/issues/3585).

Contract: on the previous base, a `createProjection` that kept the draft in an external subscription and wrote after the derivation returned lost the write (`length` stayed 0), without a warning or an error. On the verified base the draft holds until the next run of the derivation or the disposal of the owner, also for `createStore(fn, seed)` and `createOptimisticStore(fn)`: the late write reaches the effect without an explicit `flush`, and the rerun drops the previous draft.

Approach: prefer writing to a source and letting the derivation recompute. A late write through the draft only holds until the next run; keep `onCleanup(unsubscribe)` for the external subscription.

## R11: static text child of an element with spread goes out unescaped in SSR

Sources: [issue #3557](https://github.com/solidjs/solid/issues/3557), [changesets in the consulted revision](https://github.com/solidjs/solid/tree/45407d167a19a4e99af84b8076bdfa55c85c180b/.changeset).

Contract: on the previous base, `<div {...props}>a &lt;b&gt;</div>` was not escaped in SSR by either compiler (output `"a <b>"`), and the Babel plugin moved the `value` of a `textarea` with spread to children with the wrong precedence. Fixed on the verified base: the native compiler and the Babel plugin emit `"a &lt;b>"`, and Babel keeps the order between spread and `value`.

Approach: when relying on a compiler older than the verified base, check the generated HTML when an element with spread has static text with entities.

## R12: `ssrSource: "hybrid"` can lose the first response or flash the fallback

Sources: [issue #3498](https://github.com/solidjs/solid/issues/3498), [issue #3574](https://github.com/solidjs/solid/issues/3574).

Contract (without a local reproduction): in streaming hydration, the delivery of a `hybrid` source from the server to the client could lose the first response or reopen the pending window and render the fallback again on the previous base. The upstream fixes are in the tag of the verified base, without a local reproduction.

Approach: with `hybrid` and a stream, test hydration in the browser, observing the first value and the absence of a fallback after the server HTML.

## R13: zero or NaN as the only child piles up text nodes when switching

Sources: [fix #3573](https://github.com/solidjs/solid/pull/3573).

Contract: on the previous base, switching between `0` (or `NaN`) and `<span>elem</span>` as the only child piles up text nodes in `innerHTML`; in the zero case, `"0"`, `"00"`, `"000"`, without a limit. A control with the string `"zero"` does not pile up. Fixed on the verified base (the renderer clears the falsy primitive when swapping the content, `@solidjs/web/dist/web.dev.js`): in Chromium, three cycles between `0` and the element leave `0` on the verified base and `0000` on the previous base; with `NaN`, the verified base leaves `NaN`.

Approach: in the reproduction, the expression must deliver `0` or `NaN` to the renderer in one phase and an element in the other. `{n() || <Empty />}` does not exercise that path: it swaps both numbers for the fallback. Use a real browser; happy-dom erases the zero of `textContent` on its own.
